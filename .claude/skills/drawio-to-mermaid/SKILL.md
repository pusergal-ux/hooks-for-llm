# drawio → Mermaid

Обычные парсеры drawio читают только formal `source`/`target` у `mxCell`, и
любая стрелка, которую архитектор просто подвёл к фигуре мышкой, у них
теряется. Этот скилл восстанавливает такие связи в два прохода:

1. **Геометрия (скрипт)** — для рёбер без formal-привязки ищет ближайшую фигуру
   к концу линии. Уверенные решения принимаются сразу; сомнительные
   (фигура не найдена, или несколько наложенных фигур на равном расстоянии)
   помечаются `needs_review: true`.
2. **Семантика (ты)** — только помеченные рёбра разбираются по смыслу подписей
   ребра и узлов-кандидатов. Уверенные рёбра на второй проход не попадают —
   так меньше шансов "исправить" то, что и так верно.

## Шаг 0: зависимости

- Python **3.10+** (скрипт использует синтаксис `str | None`), без сторонних пакетов.
- `jq` — желательно; если его нет, ниже дана замена на Python.

## Шаг 1: геометрический проход

Запускать **из корня проекта**:

```bash
python .claude/skills/drawio-to-mermaid/scripts/drawio_to_mermaid.py <diagram.drawio> --format json -o graph.json
```

Полезные флаги:
- `--threshold 40` — радиус поиска фигуры у конца линии в px (по умолчанию 30).
  Увеличивай, если много `UNRESOLVED` при явно подведённых стрелках; уменьшай,
  если на плотной диаграмме в кандидаты лезут соседние фигуры.
- `--debug` — печатает в stderr решения по наложениям и нерезолвленные рёбра.
- `--format mermaid` (по умолчанию) — сразу mermaid без второго прохода; годится,
  только если на шаге 2 окажется, что проверять нечего.

Промежуточные `graph.json` / `edges_for_review.json` клади во временную папку
(scratchpad), а не в репозиторий пользователя — это рабочие файлы, не результат.

## Шаг 2: отобрать сомнительные рёбра

```bash
jq '[.edges[] | select(.needs_review)]' graph.json > edges_for_review.json
```

Без `jq`:

```bash
python -c "import json,sys; g=json.load(open(sys.argv[1],encoding='utf-8')); json.dump([e for e in g['edges'] if e.get('needs_review')], open(sys.argv[2],'w',encoding='utf-8'), ensure_ascii=False, indent=2)" graph.json edges_for_review.json
```

Если получился пустой список `[]` — второй проход не нужен: переходи к шагу 4
(можно просто перезапустить скрипт с `--format mermaid -o <name>.mmd`).

## Шаг 3: семантический проход (только если есть что проверять)

Прочитай [references/semantic_resolution_prompt.md](references/semantic_resolution_prompt.md) —
там правила выбора кандидата, формат ответа `<resolution>` и разобранный пример.
Ты сам выступаешь в роли резолвера: отдельный вызов модели не нужен.

Главное из тех правил, чтобы понимать их смысл:
- выбирать можно **только** из `source_candidates`/`target_candidates` этого ребра —
  id вне списка означает связь, которой на диаграмме нет;
- если смысловой причины предпочесть одного кандидата нет — `unclear`, а не первый
  по списку: ложно уверенная связь хуже явно помеченного пробела;
- смотри на подписи ребра и узлов и на общее направление потока диаграммы
  (весь `graph.json` у тебя есть — используй его как контекст).

При большом числе рёбер разбирай партиями по 10–15, держа в голове название
диаграммы и домен.

## Шаг 4: собрать итоговый mermaid

Замёржи решения шага 3 в граф по `edge_id` и собери `flowchart` по тем же
правилам, что `render_mermaid()` в скрипте (скрипт пересчитывает геометрию
с нуля и готовый JSON не принимает, поэтому строки собираешь сам):

- id узла: `n` + исходный id, где всё кроме `[a-zA-Z0-9_]` заменено на `_`;
- объявляются только узлы, участвующие хотя бы в одной связи;
- подпись узла/ребра — в двойных кавычках, внутренние `"` заменены на `'`;
- ребро: `nA -->|"подпись"| nB` или `nA --> nB` без подписи.

Рёбра с `confidence: low` или со стороной `unclear` не выдавай за окончательные:
перед их строкой ставь `%% requires manual review: <edge_id> — <reason>`
(комментарий mermaid). Если сторона `unclear` и узла нет вовсе, строку ребра не
рисуй, а оставь только этот комментарий. Если результат кладётся в markdown
вне блока ```` ```mermaid ````, допустим и `<!-- requires manual review: <edge_id> -->`.

## Шаг 5: доложить

Коротко сообщи пользователю:
- сколько рёбер было formal / привязано геометрией / отправлено на семантический
  разбор (`resolution` в `graph.json` это показывает);
- какие рёбра остались на ручную проверку и почему — одной строкой на ребро;
- куда сохранён результат.

Если в проекте есть инструмент синхронизации диаграмм (например,
`tools/src/js/sync_diagram.js` из этого же репозитория — держит `.mmd`/`.md`/`.svg`
в синхроне), предложи прогнать через него итоговый `.mmd`.

## Известные ограничения

- **Многостраничные диаграммы.** Для сжатого формата берётся только первая
  `<diagram>`; для несжатого все страницы сливаются в один граф с пересекающимися
  координатами. Для многостраничного файла предупреди пользователя и попроси
  нужную страницу отдельным файлом.
- **Вложенные фигуры.** Координаты фигур внутри групп/контейнеров/swimlane в drawio
  относительны родителю, а скрипт считает их абсолютными — геометрическая
  привязка к таким фигурам может промахиваться. Formal-рёбра это не затрагивает.
- **Изгибы линий.** Учитываются только концевые точки (`sourcePoint`/`targetPoint`),
  промежуточные waypoints игнорируются.
- Домен в system prompt reference-файла — Digital Accounting (банковский учёт).
  Для диаграмм из другого домена подставь свой домен и примеры терминов в рассуждении.
